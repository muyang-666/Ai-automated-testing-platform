## 一、核心规则

### 规则 1：不允许自行扩大需求

- 严格按照用户给定的任务范围执行
- 不得自行添加未被要求的功能、优化、重构
- 如果发现任务范围不清晰，先向用户确认再执行
- 禁止"顺手"修复无关问题或"顺便"做额外改进

### 规则 2：不允许修改未指定文件

- 只修改用户明确指定的文件或任务必需的文件
- 修改前先列出将要改动的文件清单，获得确认后再执行
- 即使发现其他文件有代码风格问题或潜在 bug，也不得在本次任务中修改
- 可以在回复中备注发现的问题，但不得擅自修改

### 规则 3：修改代码前必须先输出方案和改动文件列表

- 在动手修改任何代码之前，先输出：
  1. 方案思路（要做什么，怎么做）
  2. 将要修改/新增的文件完整列表
  3. 每个文件的修改概要
- 获得用户确认后再开始编码

### 规则 4：每次只完成一个小任务

- 一个任务 = 一个明确的、可验证的功能点或改动
- 不要把多个独立任务合并在一次修改中
- 完成一个任务后，等待用户确认再进行下一个

### 规则 5：复杂问题两轮修复失败后停止改代码

- 如果同一个问题尝试修复 2 次仍然失败，停止修改代码
- 转为诊断模式：输出问题分析、可能原因、建议的调查方向
- 等待用户给出指示后再继续
- 不要反复尝试不同的修复方案

### 规则 6：不允许破坏已有核心链路

以下链路是 V1.5 已经稳定运行的核心闭环，任何修改都不得破坏：

1. **AI 代码生成链路**：用例 → `ai_service.generate_test_code()` → LLM → pytest 代码 → 入库 + 落盘
2. **规则生成链路**：用例 → `ai_service.generate_rule_case_code()` → 确定性生成 → pytest 代码 → 入库 + 落盘
3. **pytest 执行链路**：用例 → `run_service.execute_case_test()` → `pytest_runner.py` → subprocess pytest → 结果解析 → 入库
4. **AI 分析链路**：失败执行记录 → `analysis_service.analyze_failure()` → LLM → 分析结果入库
5. **场景执行链路**：场景 → `scene_service.execute_scene()` → 逐步骤执行 → 首失败停止
6. **报告生成链路**：`report_service.generate_project_report()` → 自动执行全部场景 → LLM 汇总 → 入库

验证方法：每次修改后，至少测试一条核心链路是否仍然正常工作。

## 二、第一阶段范围约束

### 2.1 第一阶段只做

以下功能是第一阶段允许实现的：

1. 新增项目管理（`projects` 表 + CRUD）
2. 新增模块目录树（`modules` 表 + 多级树 + CRUD）
3. 给 `api_cases` 增加字段：`project_id`、`module_id`、`case_type`、`source`、`priority`、`status`、`is_deleted`
4. 用例管理页支持按项目筛选
5. 用例管理页支持按模块筛选
6. 新建/编辑用例时可选择项目和模块
7. 保留所有已有功能

### 2.2 第一阶段暂不做（绝对禁止）

以下功能明确不在第一阶段范围，**不允许以任何理由提前实现**：

1. 需求文本管理
2. 功能测试用例管理
3. 功能测试用例生成
4. 用户登录注册
5. 权限管理
6. 场景管理按项目过滤
7. 报告按项目过滤
8. 生成代码目录按项目/模块拆分
9. MySQL 切换
10. 多环境管理
11. 接口信息和接口用例彻底拆分

> AI 编码助手不得以"提前规划"、"预留扩展"、"最佳实践"等理由提前实现以上功能。

## 三、核心文件禁止修改规则

以下 6 个文件在第一阶段 **完全禁止修改**：

| 文件 | 承载的链路 | 禁止级别 |
|------|-----------|---------|
| `backend/app/services/ai_service.py` | LLM 代码生成引擎 + 规则生成引擎 | 🔴 完全禁止 |
| `backend/app/services/run_service.py` | 测试执行编排 | 🔴 完全禁止 |
| `backend/app/services/analysis_service.py` | AI 失败分析 | 🔴 完全禁止 |
| `backend/app/services/report_service.py` | 项目报告生成 | 🔴 完全禁止 |
| `backend/app/utils/pytest_runner.py` | pytest subprocess 执行器 | 🔴 完全禁止 |
| `backend/app/utils/file_writer.py` | 测试代码文件落盘 | 🔴 完全禁止 |

禁止范围：
- ❌ 不允许新增函数
- ❌ 不允许新增参数
- ❌ 不允许修改已有逻辑
- ❌ 不允许修改 import 语句
- ❌ 不允许修改函数签名
- ❌ 不允许"重构"或"优化"

> 以上文件在第一阶段中 **一行代码都不能改**。如果改造过程中发现必须修改以上文件才能完成目标，则停止改造，重新设计方案，在不修改这些文件的前提下实现目标。

## 四、默认项目与默认模块规则

### 4.1 默认测试项目
- 系统允许创建一个"默认测试项目"
- 旧 Demo 数据如果存在，可临时归属到默认测试项目
- 新增用例时 `project_id` **必须指定**，不允许为空
- 编辑用例时不允许将 `project_id` 置空

### 4.2 module_id 规则
- `module_id` 可以为空（null）
- 如果用户没有选择模块，用例归属到"未分类"
- 第一阶段**不强制**所有用例必须有 `module_id`

### 4.3 "未分类"默认模块
- 可以在每个项目下创建一个名称为"未分类"的默认模块
- 默认模块不可删除
- 默认模块的 `parent_id` 为 null（一级模块）

---

## 五、模块删除规则

1. **仅允许删除空模块** — 模块下无子模块且无用例时才能删除
2. 如果模块下存在子模块，**不允许删除**
3. 如果模块下存在接口测试用例（含软删除用例），**不允许删除**
4. **删除校验必须以后端为准** — 前端只负责提示后端返回的错误信息
5. **第一阶段不做级联删除**

---

## 六、模块排序规则

1. 第一阶段支持**同级排序**（同一父模块下的子模块之间排序）
2. 通过上移/下移或 reorder 接口调整 `sort_order`
3. 第一阶段**不强制实现跨父模块拖拽**
4. 如果实现 move 接口，只作为后端能力保留，前端可暂不开放复杂拖拽

## 七、编码约定

### 后端（Python / FastAPI）

- 文件命名：`snake_case`（如 `ai_service.py`）
- 类命名：`PascalCase`
- 函数/变量：`snake_case`
- 分层：`router → service → model/schema`，不在 router 中写业务逻辑
- 所有 API 返回 JSON
- 数据库会话通过 `get_db()` 依赖注入
- LLM 调用通过 `httpx`，不引入额外 SDK

### 前端（React）

- 页面组件：`PascalCase`（如 `CasePage.jsx`）
- 工具函数：`camelCase`
- 使用 Ant Design 组件保持 UI 一致
- API 调用封装在 `src/api/` 目录

### 数据库（SQLite + SQLAlchemy）

- 表名：`snake_case` 复数（如 `api_cases`）
- 外键：`{关联表单数}_id`（如 `case_id`）
- 通用字段：`id`（主键）、`created_at`、`updated_at`
- 不切换数据库，保持 SQLite

## 八、改造原则

1. **基于现有 Demo** — 不从零重写
2. **增量修改** — 新增功能优先通过新增文件实现
3. **向前兼容** — 新增字段给默认值，新增参数给可选
4. **保留回滚能力** — 每个改造点完成后通过 git commit 保存里程碑
