## 七、测试环境要求

1. 禁止连接真实 MySQL。
2. 禁止调用真实 LLM。
3. 禁止读取真实 API Key。
4. 禁止访问网络。
5. 使用 SQLite 测试数据库。
6. 必须在导入 `app` 前设置测试 DATABASE_URL，避免 `database.py` 初始化真实 MySQL。
7. 每条测试相互隔离，不能依赖执行顺序。
8. Fake LLM 输出使用固定 fixture。
9. 测试失败时输出中不能出现 Secret。

## 八、必须覆盖的 Baseline 行为

### A. 功能用例生成 Service

至少覆盖：

1. 有效需求 + Fake LLM JSON → 返回一条结构化候选。
2. 生成阶段只返回预览，不直接写入 function_cases。
3. Prompt 包含需求标题、内容和 supplementary_prompt；不要断言整个 Prompt 完全文本。
4. 非法 JSON → cases 为空并返回解析错误。
5. 候选缺少 case_name、steps_json、expected_result → 被校验拒绝并返回错误。
6. 模型场景未配置 → 返回当前约定的配置错误，不调用真实模型。
7. 保存候选 → source=llm。
8. 保存时 project_id 以后端 RequirementDoc 为准，不信任前端 project_id。
9. requirement 不存在 → 不调用模型并返回当前错误合同。

### B. 接口用例生成 Service

至少覆盖：

1. 有效 ApiDocument + Fake LLM JSON → 返回结构化候选。
2. 生成阶段不直接写入 api_cases。
3. 使用业务场景 `api_doc_to_api_case`。
4. Prompt 包含文档内容和 supplementary_prompt；不要断言整个 Prompt 完全文本。
5. method 和 priority 按现有规则规范化。
6. 非法 JSON → cases 为空并返回解析错误。
7. 缺少 name/url 等字段时，冻结当前 fallback 行为。
8. LLM 调用异常 → 返回当前错误合同。
9. 保存候选 → source=llm，headers/body/expected_result 保持当前 JSON 存储行为。
10. 保存时 project_id 以后端 ApiDocument 为准，不信任前端 project_id。
11. document 不存在 → 不调用模型并返回当前错误合同。

### C. 生成权限

至少覆盖：

1. tester 对已授权且 can_operate=true 的项目拥有写权限。
2. tester 对未授权项目返回 403。
3. viewer 即使存在项目记录也不能执行生成/保存写操作。

优先测试 permission_service 的确定性权限规则。只有测试基础设施已经稳定时，再考虑 Router API 集成测试，不要扩大本任务。

## 九、Baseline 原则

- 测试冻结当前行为，不在本任务顺手修复业务缺陷。
- 如果发现 bug，先让测试描述当前事实，再在开发记录中登记独立问题。
- 不要为测试通过而放宽断言。
- 不要断言容易随 Prompt 文案变化的完整字符串。
- 不使用 sleep、真实网络或随机业务数据。
- Fixture 使用虚构的登录需求和接口数据。
