# 二、Bug 1：多个 Follow-up 消息显示顺序错误

## 当前错误

用户快速发送：

```text
问题 A
问题 B
```

当前 UI：

```text
问题 A
问题 B

回答 A
回答 B
```

这是错误的。

## 正确显示

逻辑上应该按照 Turn 分组：

```text
问题 A
回答 A

问题 B
回答 B
```

如果 B 在 A 回答期间发送，应可以暂时显示：

```text
问题 A
[AI 正在回答 A...]

问题 B
Queued
```

但 A 完成、B 开始后，最终历史必须呈现：

```text
问题 A
回答 A

问题 B
回答 B
```

---

## 正确的数据模型

不要简单：

```javascript
messages.map(...)
```

按照数据库 Message sequence 全局平铺。

因为 Follow-up 的 UserMessage B 可能在 Assistant A 之前就已经持久化：

```text
sequence:
A user
B user
A assistant
B assistant
```

DB 的物理 sequence ≠ 用户界面 Turn 顺序。

前端应建立：

```text
Conversation
└─ Turns
   ├─ Turn A
   │  ├─ UserMessage A
   │  ├─ Tool events A
   │  └─ AssistantMessage A
   │
   └─ Turn B
      ├─ UserMessage B
      ├─ Tool events B
      └─ AssistantMessage B
```

优先使用：

```text
run_id
user_message_id
owner turn
```

作为归组依据。

不要靠：

```text
“遇到下一个 UserMessage 就认为上一轮结束”
```

因为 Follow-up 已证明这种算法错误。

# 三、建立统一 ChatTurn ViewModel

建议增加一个前端纯函数 / selector：

```text
buildConversationTurns(messages, runs, events)
```

最终返回概念结构：

```javascript
[
  {
    runId,
    userMessage,
    assistantMessages,
    toolEvents,
    status,
    queueState,
    startedAt,
    finishedAt
  }
]
```

UI 永远：

```javascript
turns.map(turn => <ChatTurn ... />)
```

而不是分别：

```javascript
messages.map(...)
toolEvents.map(...)
```

这一层必须成为修复 Bug 1 和 Bug 2 的核心。

# 四、Bug 2：旧 Tool 调用一直显示在聊天最底部

## 当前错误

例如：

```text
User A
Assistant A

User B
Assistant B

calculator(A)
```

甚至每次新回答后：

```text
calculator(A)
calculator(A)
...
```

一直挂在整个 Conversation 最后。

这说明：

> Tool events 当前是 Conversation 级列表，而不是 Turn 级内容。

---

## 正确行为

Tool 调用必须属于产生它的 Run：

```text
问题 A

┌ Tool
│ calculator
│ ✓ completed
└
回答 A

问题 B
回答 B
```

下一轮不应再次显示 A 的 Tool。

---

## 修复要求

所有：

```text
conversation_tool_started
conversation_tool_finished
```

必须根据：

```text
run_id
```

归到对应 ChatTurn。

如果 started / finished 是两个 Event：

前端应该合并成一个 ToolActivity：

```javascript
{
  toolCallId,
  toolName,
  status: "running" | "success" | "error"
}
```

不要渲染成：

```text
calculator started
calculator finished
```

两条重复聊天信息。

---

# 五、Tool activity UI 重新设计

不要把 ToolCall 做成普通聊天气泡。

改成低干扰的 inline activity，例如：

```text
○ 正在使用 calculator

✓ calculator
```

或者折叠形式：

```text
▾ Used calculator          ✓
```

默认只显示：

```text
Tool name
status
```

可以点击展开安全的参数/结果摘要。

不要显示：

- raw secret；
- internal logs；
- stack trace；
- hidden reasoning。

# 六、Bug 3：切换 Conversation 后停留在顶部

## 当前错误

打开历史 Conversation：

```text
scrollTop = 0
```

用户看到最早的问题。

## 正确

首次打开 Conversation 后：

```text
自动定位到最底部
```

显示最新 Turn，方便继续聊天。

---

## Scroll 行为必须区分场景

### 切换 Conversation

```text
scrollToBottom({ behavior: "instant" })
```

### 刷新恢复当前 Conversation

默认到底部。

### 当前用户本来就在底部

Streaming 新内容：

```text
自动跟随
```

### 用户主动向上滚看历史

不要强制把用户拉回底部。

出现浮动按钮：

```text
↓ 回到最新
```

### 用户自己发送新消息

立即滚到底部。

---

## 不要用粗暴方案

不要：

```javascript
useEffect(() => {
  scrollIntoView()
}, [messages])
```

无条件执行。

这会让用户永远无法看历史。

需要维护：

```text
isNearBottom
```

例如距离底部 < 80px 时自动 follow。

# 七、Bug 4：所有 Conversation 都叫“新对话”

需要增加 Conversation Title 行为。

---

## 首期 Title 逻辑

创建时可以暂时：

```text
新对话
```

但第一条 UserMessage 提交后自动生成临时标题。

无需再调用一次 LLM。

首期直接 deterministic：

```text
取第一条用户消息
→ 去除换行
→ trim
→ 截取约 20～30 个中文字符
```

例如：

```text
帮我分析一下登录接口的测试点
```

Conversation Title：

```text
登录接口测试点分析
```

如果不做语义摘要，也可以：

```text
帮我分析一下登录接口的测试点
```

截断显示：

```text
帮我分析一下登录接口的测试...
```

比永远“新对话”好。

---

## 推荐进一步实现

如果后端 Conversation 已有 title：

增加：

```text
PATCH /agent/conversations/{id}
```

支持：

```json
{
  "title": "登录接口测试"
}
```

前端允许：

```text
双击 / ... → Rename
```

但保持实现简单。

不要为了自动命名额外调用真实 LLM。
