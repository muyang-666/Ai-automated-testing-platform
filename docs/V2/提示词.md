# V2-P06 — Conversation API + SSE + 基础持续聊天工作台

P05 已完成。

```text
submit_conversation_turn
→ AgentRun(conversation)

→ Worker claim
```

```text

→ 当前回答未结束时继续发送 follow-up
→ Cancel
→ Refresh
→ 历史恢复
→ 继续聊
```

P06 不实现 TestArtifact、MindMap、Artifact Tool。

## 2. queued active head cancel

检查场景：

```text
A = queued + active_slot=1
B = queued + active_slot=NULL

用户在 Worker claim A 之前 cancel A
```

当前必须最终得到：

```text
A cancelled
B promoted → active_slot=1
```

不能让 B 永远留在 NULL slot。

将 promotion 放在正确的 conversation cancel application-service/API 边界，并保持原子性。

同时验证：

```text
取消 queued follow-up B
```

仍只是取消 B，不错误 promote C，因为当前 head A 仍在。

补针对性测试。

# 四、创建 Conversation

允许：

```text
project_id = null
```

用户登录后不选择项目也能聊天。

请求概念：

```json
{
  "title": "New conversation",
  "project_id": null
}
```

owner 必须来自：

```text
get_current_user
```

不得接受客户端提供 user_id。

只返回当前用户自己的 Conversation。

# 五、Submit Turn

新前端发送消息只能调用一次：

```text
POST /agent/conversations/{id}/turns
```

请求：

```json
{
  "content": "你好",
  "client_request_id": "uuid",
  "queue_mode": "follow_up"
}
```

返回 202，例如：

```json
{
  "run_id": 123,
  "user_message_id": 456,
  "replayed": false,
  "queue_state": "executable"
}
```

内部直接复用：

```text
conversation_service.submit_conversation_turn()
```

不要重新写一套：

```text
save message
create run
idempotency
active_slot
```

逻辑。

前端不再：

```text
appendMessage
→ createCaseGenerationRun
```

# 六、Conversation snapshot

`GET /agent/conversations/{id}` 应能给前端恢复基本状态：

```text
conversation metadata

queue state

```

具体 schema 保持最小。

不要把 500 条 Message 全塞进 conversation detail。

Message 使用单独 endpoint。

# 七、Message API

建议支持：

- user；

# 八、SSE

实现：

```text
GET /agent/conversations/{id}/events
```

技术合同以 `05_TECHNICAL_DESIGN.md §15` 为准。

必须支持：

- Bearer authentication；
- conversation owner isolation；
- event sequence cursor；
- reconnect；
- duplicate protection；
- terminal recovery；
- 慢客户端不阻塞 Worker；
- Token 不放 URL；
- 不输出隐藏 reasoning。

如果 EventSource 无法携带现有 Bearer：

使用 fetch + ReadableStream SSE parser，或项目当前合适方式。

不要为了方便把 access token 放 query string。

# 十、AgentLoop execution event

检查 P05 当前：

```text
event_sink
```

是否仍只保存到 Runner 内存 list。

P06 要把安全可展示的 Agent execution event 接到持久化/广播边界。

重点：

```text

```

```text

```

# 十一、Streaming persistence

不要每个 token 创建一条 AgentEvent DB row。

推荐：

```text
text delta
→ transient SSE batching/broadcast
```

而：

```text
assistant message end
tool lifecycle
run terminal
```

有稳定持久化状态。

SSE 断线后：

```text
GET messages / events snapshot
```

能恢复正确结果。

# 十二、Provider 配置

P05 当前 Conversation Worker 使用 env ProviderSnapshot 是 transitional。

P06 收敛成现有 LLM 配置系统里的独立聊天场景，例如：

```text

```

或仓库当前最合理 scene。

要求：

- Provider/model 来自服务端配置；
- Secret 不返回前端；
- API Key 不写 Message/Event；
- 未配置时返回固定 configuration_not_ready；
- 不自动生成/写入真实 Key；
- CI 使用 Fake Provider。

真实供应商验证仍留 P10。

# 二十一、Follow-up

P05-E 已完成。

P06 只负责 API/UI 接入，不重新设计 Queue。

场景：

```text
A streaming

用户发送 B
用户发送 C

UI:
A running
B queued
C queued
```

```text
B 自动执行
```

前端通过 Event/refresh state 得知，不自己 promote。

# 二十二、Error 后继续

如果当前 Turn：

```text
failed / interrupted
```

后续 queue 会 paused。

用户必须仍然可以：

- 查看错误；
- 查看已保存历史；
- 新建 Conversation；
- 做现阶段已定义的安全继续操作。

如果“恢复 paused queue”的正式产品合同尚未在 P06 定义，不要擅自设计复杂恢复状态机；可以只展示 paused 并留 P10/P后续明确处理。

但 P06 Acceptance 中“错误后可以继续聊”需要明确实现方式，并与 P05 paused 语义一致。

不要通过偷偷把 failed 改 succeeded 解决。
