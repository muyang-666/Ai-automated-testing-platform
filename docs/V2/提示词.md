# P05-E — Conversation Follow-up Queue 与连续 Turn 调度语义

目标：

在 P05-C/P05-D 已完成的：

```text
submit Turn
→ queued Run
→ Worker claim
→ ConversationRunner
→ Agent Loop
→ heartbeat / fencing / cancel / terminal
```

基础上，让同一个 Conversation 在当前 Turn 仍运行时，用户可以继续发送消息。

本阶段解决的是：

```text
Turn A running

用户继续发：
Turn B
Turn C

→ 不再直接 conversation_conflict
→ B/C 按提交顺序排队
→ A 完成后 B 执行
→ B 完成后 C 执行
```

同时必须定义：

- 前一 Turn 成功后如何继续；
- 前一 Turn failed / interrupted 时后续队列如何处理；
- cancelled 后是否继续；
- 幂等重试如何保持；
- 同一 Conversation 绝不并行执行两个 Turn。

不要实现 Pi steer，不修改正在执行 Turn 的上下文，不做用户消息抢占，不做 P06 HTTP/SSE/UI。

## 2. P05-D preflight

开始实现 follow-up 前，先核验两个 reliability 边界：

### A. stale recovery TOCTOU

最终 `running → interrupted` 的原子 UPDATE 必须重新包含 stale 条件，并在适用时校验 expected execution token。

不能：

```text
find stale
→ 中间 heartbeat 已刷新
→ 只按 status=running mark_interrupted
```

若当前代码仍有该问题，本阶段允许做最小修复并补测试。

### B. MySQL heartbeat rowcount=0

若 fenced heartbeat UPDATE 返回 0，ownership probe 必须重新 SELECT 并判断：

```text
status == running
AND worker_id == current_worker
AND execution_token == current_token
```

若三者仍匹配，应视为 ownership 仍有效，而不是直接 lost。

若当前代码已正确，不重复修改。

## 3. 核心语义：follow-up ≠ steer

### Follow-up

```text
Turn A 正在执行
用户发送 Turn B
→ B 排在 A 后面
→ 不影响 A 当前 Agent Loop
```

### Steer

```text
Turn A 正在执行
用户发送新指令
→ 尝试影响 A 接下来的模型轮次
```

P05-E **只实现 follow-up**。

不要把 B 注入 A 当前 `context.messages`。

---

## 4. Conversation 顺序模型

最终必须保证：

```text
Conversation
├─ Turn A  running
├─ Turn B  queued_follow_up
└─ Turn C  queued_follow_up
```

执行：

```text
A success → B → C
```

同一个 Conversation：

```text
max running Turn = 1
```

不同 Conversation 可并行。

---

## 5. Follow-up 必须持久化

禁止 Python 内存 queue 作为 Source of Truth。

优先复用：

```text
AgentMessage
AgentRun
message sequence
active_slot
```

## 6. active_slot 建议语义

当前 `active_slot=1` 用于防同会话多个 active Turn。

推荐：

```text
queued follow-up
= 已创建 UserMessage + AgentRun
= active_slot=NULL

当前可执行 head
= active_slot=1
```

当前 Turn 终态后：

```text
promote next queued follow-up
→ active_slot=1
```

promotion 必须数据库原子裁决。

若当前 schema 无法安全表达，可做最小 migration，但不要设计复杂 DAG。

---

## 7. submit_conversation_turn

支持明确 `queue_mode`：

```text
follow_up
reject
```

### follow_up

active Run 存在：

```text
保存 UserMessage
保存 queued Run
active_slot=NULL
```

### reject

保持 409。

幂等合同保持：

- same key + same content → replay；
- same key + different content → conflict。

---

## 8. 最关键：Run-bounded Context Restore

A 执行期间 B 可以已经写入 DB。

因此 ConversationRunner 不能再简单 restore 当前 Session 全部 Message。

必须：

> 当前 Run 只能恢复截至自己的 user_message_id / message sequence 的历史。

例如：

```text
A user seq=10
B user seq=11
```

A 只恢复：

```text
sequence_no <= 10
```

A 永远不能看到 B。

B 开始时应该看到：

```text
A user
A assistant/tool result
B user
```

必须用测试证明。

---

## 9. Promotion

建议集中 service：

```text
promote_next_conversation_run(session_id)
```

语义：

1. 当前没有 active_slot=1；
2. 找最早 queued follow-up；
3. 条件 UPDATE active_slot=1；
4. commit。

两个并发 promotion 只能一个成功。

---

## 10. Worker claim

Conversation Run 只能 claim：

```text
status=queued
AND active_slot=1
```

不能提前 claim：

```text
active_slot=NULL
```

全局候选查询不能因不可执行 follow-up 阻塞其他 Session。

Legacy 不回归。

---

## 11. Terminal queue semantics

### succeeded

```text
promote next
```

### cancelled

首期建议：

```text
promote next
```

即取消当前回答，不自动删除用户已经提交的后续 Turn。

### failed / interrupted

按现有技术设计：

```text
pause queue
```

后续 queued Run 不 promote。

P06 UI 再向用户解释 paused。

---

## 12. queued follow-up cancel

允许：

```text
queued → cancelled
```

promotion 自动跳过 cancelled。

---

## 13. failed-head handling

需要能派生：

```text
waiting
paused
executable
```

即使不新增 DB status，也应有 service/query 能告诉 P06 前端真实 queue_state。

## 14. Pi 对照

参考 Pi followUp：

- 当前 run 完成后进入下一 Turn；
- 不等价于 steer；
- 不把 follow-up 注入正在执行的工具/模型轮次。

TestMind 差异：

> Pi 可用内存 stateful Agent；TestMind follow-up 必须持久化并适配 Worker/DB。

## 15. Tests

至少：

1. A running 时 submit B → B persisted but not claimable；
2. A running 时 submit B/C → 顺序稳定；
3. A success → only B promoted；
4. B success → C promoted；
5. 不同 Conversation 不被 B/C 阻塞；
6. A failed → B/C paused；
7. A interrupted → paused；
8. A cancelled → 按最终合同 promote next；
9. queued B cancel → promotion skip B；
10. idempotent follow-up；
11. Run-bounded restore：A 看不到 B；
12. B 执行时看到 A 完整结果；
13. 双连接 promotion race 最终只有一个 active_slot；
14. P05-D reliability 回归。
