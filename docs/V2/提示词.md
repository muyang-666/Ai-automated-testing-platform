# P05-D — Worker Execution Ownership Reliability

目标：

在 P05-C 已经完成：

```text
queued Run
→ atomic claim
→ Worker dispatch
→ ConversationRunner / AgentRunner
```

的基础上，补齐长时间 Agent 执行时的：

- lease
- heartbeat
- stale recovery
- fencing token
- Worker 层 cancel propagation

核心要解决：

> Worker 在开始时成功 claim Run，并不代表它执行几分钟后仍然拥有这个 Run。

本轮不要实现 P05-E follow-up，不要开始 P06/P07/P08，不要重构成复杂并发 Worker Pool。

# 2. 已完成前提

P05-C 当前真实语义：

```text
next_queued_run_id()
→ claim_queued_run()
→ queued → running
→ 写 worker_id / heartbeat_at / started_at
→ commit

workflow_code == conversation
→ ConversationRunner

其他
→ Legacy AgentRunner
```

claim：

- 负责 atomic ownership acquisition；
- 不产生 run_started Event；
- transaction 很短；
- conversation 和 legacy 使用同一队列。

Runner：

- 负责 lifecycle event；
- 负责终态；
- ConversationRunner 内部直接调用唯一 `run_agent_loop()`。

P05-D 不允许破坏这些边界。

# 3. 本轮核心模型

需要明确区分：

## Atomic Claim

回答：

> 谁最先获得这个 Run 的执行权？

## Lease / Heartbeat

回答：

> 这个 Worker 现在是否仍然活着、是否仍然持有执行权？

## Fencing Token

回答：

> 如果旧 Worker 已经失去执行权，它还能不能继续修改这个 Run？

三者不能混为一个概念。

最终应形成：

```text
queued
  ↓
atomic claim
  ↓
worker_id + fencing_token
  ↓
running
  ↓
heartbeat refresh
  ↓
Agent executing
```

如果 heartbeat 超时：

```text
running
  ↓
stale detected
  ↓
ownership revoked
  ↓
interrupted / recoverable state
```

旧 Worker 后续写入：

```text
fencing_token mismatch
→ rejected
```

# 5. Fencing Token 设计

推荐字段语义：

```text
execution_token
```

也可沿用项目现有命名。

类型建议：

```text
integer / bigint
```

每次新的 execution ownership 获取时单调递增：

```text
Run #100

claim A
token = 1

发生 stale recovery

重新 claim B
token = 2
```

Worker A 后续所有关键写操作仍携带：

```text
token=1
```

必须被拒绝。

Worker B：

```text
token=2
```

才能继续写。

原则：

> fencing token 必须来自数据库 ownership generation，
> 不能由 Worker 自己随机生成后不校验。

---

# 6. Fencing Token 必须保护哪些写操作

至少审计并保护：

- heartbeat refresh；
- Run terminal transition；
- Run error update；
- lifecycle Event 写入；
- ConversationRunner 最终 persist/finalize；
- stale recovery 后可能发生的旧 Worker写入。

如果当前架构很难让所有底层 service 都直接接受 token，本轮可以通过：

```text
WorkerExecutionContext
```

或最小参数传递实现。

但不要造复杂框架。

核心是：

> 旧 execution generation 不能成功提交新的 Run 生命周期状态。

对于 Conversation Message 已成功生成但 fencing 已失效的情况，需要明确策略。

首期推荐：

```text
在关键持久化前先验证 ownership token。
```

如果 ownership 已失效：

- 不继续提交新的 Assistant / ToolResult；
- 不覆盖 Run terminal；
- 返回 ownership_lost / stale_execution。

不要让旧 Worker“先写消息，再发现自己过期”。

# 7. Claim 与 fencing token

`claim_queued_run()` 成功时应该原子获得：

```text
worker_id
heartbeat_at
started_at
execution_token
```

如果已有 token：

```text
execution_token = execution_token + 1
```

如果为空：

```text
execution_token = 1
```

确保两个 Worker 不可能拿到同一 generation。

返回 claim result 时，应让 Worker 获得：

```text
run_id
execution_token
```

不要执行后再额外查询并猜当前 token。

# 8. Heartbeat

目标：

Agent 长时间 await Provider 时，heartbeat 仍然更新。

当前同步 Worker：

```text
run_once
→ asyncio.run(ConversationRunner.run())
```

请先评估最小实现。

优先方案：

> 独立 heartbeat execution unit + 独立 DB Session。

可以是：

- background thread；
- 或在 conversation async execution 内创建 heartbeat coroutine；

但不要为了 heartbeat 把整个 Worker 重写成大型 async scheduler。

如果使用 async heartbeat task：

```text
runner task
+
heartbeat task
```

必须确保：

- heartbeat 使用独立 SQLAlchemy Session；
- heartbeat 不复用 Runner 当前 Session；
- heartbeat 不持有长事务；
- heartbeat task 在 Runner 完成后可靠停止；
- heartbeat exception 不悄悄吞掉；
- ownership lost 会通知主执行。

---

# 9. Heartbeat 更新必须带 fencing 条件

禁止：

```sql
UPDATE agent_run
SET heartbeat_at = now()
WHERE id = :run_id
```

应类似：

```sql
UPDATE agent_run
SET heartbeat_at = now()
WHERE id = :run_id
  AND status = 'running'
  AND worker_id = :worker_id
  AND execution_token = :execution_token
```

如果：

```text
rowcount = 0
```

意味着：

```text
ownership lost
```

此时 Worker 必须停止继续执行/持久化。

不要自动重新 claim 当前执行。

# 10. Heartbeat interval / stale threshold

不要把数字散落 hardcode。

检查 Settings。

如果没有，新增明确配置，例如概念：

```text
AGENT_HEARTBEAT_INTERVAL_SECONDS
AGENT_STALE_THRESHOLD_SECONDS
```

要求：

```text
heartbeat interval << stale threshold
```

例如测试中可：

```text
50 ms heartbeat
200 ms stale
```

生产默认值根据现有项目风格给合理值。

文档说明默认值即可。

不要为了本轮实现复杂动态配置中心。

# 11. Stale Recovery

当前如果已有 recovery：

```text
running
+ heartbeat expired
→ interrupted
```

请扩展为与 fencing 一致的语义。

恢复动作必须原子：

```text
WHERE
status = running
AND heartbeat_at < threshold
AND execution_token = old_token
```

然后：

- 撤销旧 ownership；
- 进入 interrupted / queued / recoverable 状态，按当前设计；
- 必要时清空 worker_id；
- 不允许旧 Worker 再 heartbeat；
- 后续重新执行时 token 必须递增。

不要在 recovery 时复用旧 execution_token。

---

# 12. interrupted 后怎么处理

优先遵循当前 `AgentRun` 状态机。

如果现有设计：

```text
running
→ interrupted
```

保持。

本轮不要擅自改成：

```text
running
→ queued
```

除非当前开发计划明确要求自动 retry。

P05-D 重点是：

> 正确识别 stale execution，并让旧 Worker失效。

是否自动重新排队可以保持当前已有语义。

# 13. Cancel Propagation

P05-B 的 AgentLoop 已支持：

```text
cancel_event
```

但 P05-C 报告说明：

> Worker 层 cancel propagation 仍未接。

本轮把它接通。

需要检查当前：

- cancel API/service 如何更新 Run；
- 是否有：
  - cancel_requested
  - status=cancelled
  - cancelled_at
  - cancel event
- ConversationRunner 接收的 `asyncio.Event` 当前如何使用。

目标：

```text
用户请求 cancel
      ↓
DB 状态 / cancel flag
      ↓
Worker heartbeat/control loop 定期观察
      ↓
cancel_event.set()
      ↓
AgentLoop 检查 cancel
      ↓
aborted
      ↓
ConversationRunner
      ↓
Run cancelled
```

不要使用强杀线程。

---

# 14. Cancel 与 heartbeat 可以共用 control loop

如果实现独立 background control task，可以在每个 tick：

```text
1. heartbeat
2. verify fencing ownership
3. check cancel request
```

然后：

```text
cancel requested
→ cancel_event.set()

ownership lost
→ ownership_lost_event / cancel_event.set()
```

但需要区分：

```text
用户取消
```

和：

```text
ownership lost
```

最终错误语义不要都伪装成 user_cancelled。

可以分别使用：

```text
canceled
ownership_lost
```

具体错误码以现有 contract 为准。

---

# 15. ConversationRunner 与 fencing 的关系

ConversationRunner 不应该自己定时 heartbeat。

它应该收到一个已经确定的执行上下文，例如概念：

```text
run_id
worker_id
execution_token
cancel_event
```

Runner 在关键持久化/终态前可以调用：

```text
assert_execution_ownership(...)
```

或者由 service 的 fenced write 保证。

不要让 Runner：

```text
每 10 秒自己 sleep heartbeat
```

heartbeat 属于 Worker execution ownership。

---

# 16. AgentLoop 不应该知道 fencing

`run_agent_loop()` 不应该加入：

```text
worker_id
execution_token
heartbeat
SQLAlchemy
```

AgentLoop 继续只知道：

- cancel；
- deadline；
- budget；
- tools；
- provider。

ownership 丢失时由 Worker/Runner：

```text
cancel_event.set()
```

通知 AgentLoop 尽快停止。

保持 P03 纯度。

---

# 17. Legacy Runner

本轮 heartbeat/fencing 设计需要考虑 legacy，但不要重写 legacy Workflow。

要求至少保证：

- legacy Run claim 同样获得 fencing token；
- stale legacy Run 也不会被旧 Worker继续 finalize；
- 现有 step boundary heartbeat 如果保留，要改成 fenced heartbeat；
- 不破坏 CaseGenerationWorkflow。

如果 Conversation 使用后台 heartbeat、legacy 仍使用 step heartbeat，需要明确这是临时差异。

优先考虑把 ownership control 放 Worker 层，这样两种 Runner 都能复用。

# 20. Ownership Lost 场景

这是本轮最关键测试之一。

模拟：

```text
Worker A
token=1
开始慢 LLM

测试线程：
把 Run ownership generation 改成 token=2
或执行 stale recovery / reassignment

Worker A heartbeat:
WHERE token=1
→ rowcount=0
```

然后验证：

- Worker A 识别 ownership lost；
- AgentLoop 尽快停止；
- Worker A 不写 succeeded；
- Worker A 不覆盖 token=2 执行者状态；
- 不产生错误的成功 Assistant Message。

# 21. Stale Recovery 场景

测试：

```text
Run
status=running
worker_id=A
heartbeat_at=很久以前
token=4
```

执行 stale recovery。

验证：

- Run → 当前设计规定的 interrupted 状态；
- A ownership 失效；
- A 使用 token=4 heartbeat 失败；
- 后续如果重新 claim，得到 token=5；
- token 单调递增。

# 22. Cancel 场景

Fake Provider：

```text
开始长时间 await
```

随后：

```text
request cancel
```

验证：

```text
control loop
→ cancel_event.set()
→ AgentLoop aborted
→ ConversationRunner
→ Run cancelled
```

并验证：

- 不等待 Provider 完整长 timeout 才响应，如果 Fake Provider 支持 cancellation；
- 不产生 final success；
- run_cancelled event 恰好一次。

如果 provider 调用本身无法被 cancel_event 中断，只能在模型调用结束后检查，也要真实记录这个限制，不要谎称即时取消。

# 23. Heartbeat Failure

模拟 DB heartbeat update 抛异常。

不要简单吞掉。

策略需要明确：

推荐：

```text
连续 heartbeat/control failure
→ execution safety uncertain
→ stop current execution
```

至少测试：

- Worker 不继续假装 ownership 正常；
- Run 不被错误标 succeeded。

首期可以一次 heartbeat failure 即安全中止，避免复杂 retry。

如果实现少量 retry，请保持简单。

---

# 24. Event

不要每次 heartbeat 都写 AgentEvent。

否则：

```text
10 秒一个 heartbeat
```

会制造大量日志。

heartbeat 只更新 Run heartbeat 字段。

Event 仅在关键 lifecycle：

```text
run_started
run_interrupted
run_cancelled
ownership_lost（如现有 Event 合同允许）
```

不要创造噪声事件。

- existing rows 安全；
- downgrade 明确；
- 不修改无关字段；
- 不引入队列表。

如果已有可作为 generation 的字段，优先复用，不重复新增。
