## 八、工具公共规则

每个 Tool 必须具有：

- 唯一 name；
- 明确 description；
- Pydantic input_model；
- Pydantic output_model；
- read_only；
- requires_approval；
- idempotent；
- required_permission；
- handler。

公共 ToolContext 至少包含：

- db
- requester_user_id
- project_id
- session_id/run_id，可空

每次工具执行时必须重新校验项目权限，不能只相信 Runtime 创建 Run 时的鉴权。

## 九、Tool 1：load_source_context

输入：

- source_type：requirement/api_document
- source_id

输出：

- source_type/source_id
- project_id/module_id
- title/name
- 结构化 source_data
- source_hash
- warnings

要求：

- 不存在、软删除或无权限时返回稳定工具错误；
- source_hash 使用稳定规范化 JSON + SHA-256；
- ApiDocument 应包含当前已有的 method/url/headers_json/params_json/body_json/response_example_json/content；
- RequirementDoc 应包含 title/content/type/status/supplementary_prompt；
- Secret 字段脱敏后才能进入 Tool 输出；
- 不修改来源数据。

## 十、Tool 2：load_project_module_context

输入：project_id/module_id。

输出：

- project 摘要；
- module 摘要；
- module breadcrumb；
- warnings。

要求：

- 校验读取权限；
- module 必须属于当前 project；
- module_id 为空时允许返回项目级上下文；
- breadcrumb 必须设置最大深度和循环保护；
- 不返回无关项目数据。

## 十一、Tool 3：list_existing_cases

输入：

- source_type
- project_id/module_id
- requirement_id，可空
- method/url，可空
- limit，必须有上限

输出仅保留去重和提示所需字段。

要求：

- requirement：优先查询同 requirement_id 的 FunctionCase，再按项目/模块补充；
- api_document：当前 APICase 没有 document_id，不得伪造直接关联；只能按 project/module/method/normalized_url 等现有字段检索，并返回 limitation warning；
- 默认排除软删除；
- 严格限制数量；
- 不返回 generated_test_code、完整 Secret headers 或无关大字段；
- 每次调用重新鉴权。

## 十二、Tool 4：list_related_api_documents

输入：project_id/module_id/keyword/limit。

要求：

- 只查询当前项目；
- 当前没有 RequirementDoc→ApiDocument 显式关系时，不得声称找到精确关联；
- 可以按相同 module 和关键词返回候选，并明确 `relation_type=module|keyword|none`；
- 输出限制字段和数量；
- 所有内容脱敏。

## 十三、Tool 5：validate_case_schema

支持两类候选：

- function_case
- api_case

使用 Pydantic 合同验证：

- 必填字段；
- 数据类型；
- steps_json 必须为非空字符串数组；
- test_data_json 必须为对象；
- method/case_type/priority 枚举；
- URL 字段类型；
- expected_result 类型。

输出：

- valid_candidates
- invalid_candidates
- errors：candidate_id/path/code/message

错误中不回显完整敏感输入。

## 十四、Tool 6：validate_case_business_rules

确定性规则至少包括：

### 功能用例

- case_name 非空；
- steps 非空且每步非空；
- expected_result 非空；
- case_type/priority 合法；
- covered_clause_ids 非空且不重复；
- 未知假设必须显式记录。

### 接口用例

- method 合法；
- URL 非空且与来源文档不冲突；
- headers/body 类型合法；
- expected_result 可验证；
- 参数不能在文档完全无依据时静默当作事实；
- Secret 不能出现在错误摘要或指纹中。

本任务只判断，不自动修改候选。

## 十五、Tool 7：deduplicate_cases

首期只做确定性去重，不使用 embedding 或 LLM Judge。

要求：

- 规范化大小写、首尾空格、连续空白；
- API 用例至少考虑 method + normalized_url + canonical body/params + expected；
- 功能用例至少考虑 normalized name + steps + expected；
- 同时比较候选内部和已有用例；
- 输出 duplicate_candidate_id、matched_id、duplicate_type、fingerprint；
- 不使用难以解释的随意相似度阈值；
- 如果使用 `difflib` 做 advisory，相似项只能标记 possible，不得自动删除；
- fingerprint 不包含 Secret 明文。

## 十六、Tool 8：compute_coverage_matrix

输入：

- atomic_clauses
- candidates
- requested_dimensions

要求：

- clause_id 唯一；
- candidate 的 covered_clause_ids 必须存在；
- 维度必须来自允许集合；
- 程序计算 clause × dimension 覆盖；
- 输出 covered/missing/invalid references；
- 不相信模型自报 coverage_percent；
- 分母为 0 时返回明确状态，不除零；
- 同一 candidate 重复引用不重复计数；
- P0/P1 条款可以单独汇总，但不预设虚假质量阈值。

## 十七、Tool 9：dry_run_api_case_codegen

目标：验证候选 API 用例能否通过现有确定性规则生成合法 pytest，但不产生副作用。

优先复用 `ai_service.py` 的纯函数：

- build_case_context
- validate_rule_generation_input
- generate_mock_test_code
- validate_python_code
- validate_generated_code_rules_with_reason

禁止调用：

- save_generated_code_result
- save_test_code_to_file
- generate_case_test_code_by_rule
- execute_case_test
- run_pytest_file
- 任意 httpx 请求

要求：

- 使用未加入 Session 的临时 APICase 对象或纯输入对象；
- 确认 db 中 APICase/FunctionCase 数量不变；
- 确认 tests_generated 目录没有新增/修改文件；
- 不执行生成代码；
- 输出 syntax_valid/rule_valid/reason/input_warnings；
- 不返回包含 Secret 的完整生成代码，除非明确脱敏且有当前消费者；首期优先只返回摘要。

## 十八、脱敏

如项目尚无通用脱敏工具，本任务实现最小递归脱敏：

- Authorization
- Cookie
- api_key
- access_token / refresh_token / token
- password / passwd
- secret

要求：

- key 匹配不区分大小写；
- dict/list 嵌套均处理；
- 原输入不被原地修改；
- hash/fingerprint 不包含 Secret 明文；
- 错误信息不输出完整 headers/body；
- 不尝试在任意自然语言中识别所有隐私数据，首期明确能力边界。
