## 六、两个必须修正的衔接问题

### 1. 用户拒绝不等于系统失败

当前 T06 报告称 GATE rejected → Run failed。

调整为：

```text
scope/coverage/save Approval rejected
→ AgentRun cancelled
→ 写 user_rejected 事件
→ 不设置系统失败 error_code
```

用户拒绝是正常业务终止，不应污染 Agent 失败率。

### 2. 审批后必须可被 Worker 继续执行

Worker 当前只抢占 queued，不能直接处理 waiting_approval。

采用：

```text
waiting_approval
→ 用户 approve/modify
→ Approval resolved
→ AgentRun 转为 queued
→ Worker 正常原子抢占 queued
→ Runner 根据 workflow_state 和 resolved Approval 继续
```

要求：

- 在合法状态转换中增加 `waiting_approval → queued`；
- 只有当前等待的 pending Approval 被合法解决后才能重新 queued；
- rejected → cancelled，不重新排队；
- 重复审批不得重复 requeue；
- 不由 API 线程同步执行 Runtime；
- 不把 waiting_approval 直接改 running 绕过 Worker 抢占。

## 十、权限规则

### Session

- 创建时必须拥有 project read 权限；
- 查看 Session/Message/Event：首期只允许 session owner；
- admin 审计入口不在本任务实现；
- 写消息、取消、审批、保存：只允许 session owner；
- 所有操作再次校验 project 权限；

### Run/Artifact/Approval

- 不相信请求体中的 project_id/user_id；
- 返回 404/403 的策略遵循项目现有规范，不泄露其他用户资源是否存在。

## 十一、Session 与 Message

### 创建 Session

请求：project_id、title 可空、agent_version 可空。

后端写入当前 user_id，不接受前端传 user_id。

### Message

T07 只负责持久化用户消息和必要系统状态消息，不做自然语言 Skill 路由。

- role 由接口确定，用户不能伪造 assistant/system/tool；
- 用户只提交 content/content_json 中允许字段；
- sequence_no 使用现有 Service；
- 并发竞态限制如仍存在，保留明确记录；
- content 长度设上限；
- 消息不能直接触发任意 Tool。

## 十二、创建 Run

要求：

- Session 必须 active；
- 当前用户是 owner；
- project 权限有效；
- 只允许已注册 `case_generation:v1`；
- input 使用 T06 Pydantic Schema；
- session.project_id 与 run.project_id 一致；
- source 必须属于 Session project；
- idempotency_key 必填或按最终方案明确；
- 相同 Session/Skill/idempotency_key 重复请求返回同一 Run，不重复创建；
- 创建后只写 queued，不在 API 中执行 Runtime；
- Worker 由独立 CLI 处理。

## 十四、GATE 解决与重新排队

`POST /agent/approvals/{approval_id}/resolve`

请求示例：

```json
{
  "decision": "approved",
  "resolution": {}
}
```

或修改范围：

```json
{
  "decision": "approved",
  "resolution": {
    "case_types": ["正常场景", "边界场景"],
    "max_cases": 20,
    "user_goal": "重点覆盖账号锁定"
  }
}
```

事务顺序：

```text
锁定/条件更新 pending Approval
→ 校验 resolution Schema
→ 更新 Approval
→ 写 approval_resolved Event
→ approved 时 Run waiting_approval → queued
→ rejected 时 Run waiting_approval → cancelled
→ commit
```

任一步失败整体 rollback。

幂等要求：

- 同一用户重复提交相同 decision/resolution，返回现有结果，不重复事件和 requeue；
- 已 approved 后提交不同 resolution 返回 409；
- 已 rejected 后再 approved 返回 409；
- Approval 不属于当前 Run/Session/User 返回拒绝；
- 非当前等待的 Approval 不能推进 Run。

## 十五、取消 Run

- queued → cancelled；
- running：设置 cancelled，Runner 在步骤边界停止；
- waiting_approval → cancelled，同时取消 pending Approval；
- succeeded/failed/cancelled 重复取消遵循幂等响应，不反向修改；
- 写 cancelled Event；
- 不删除 Step/Event/Artifact。

## 十六、候选保存

### 请求

```json
{
  "artifact_id": 99,
  "candidate_ids": ["CASE-001", "CASE-003"],
  "idempotency_key": "save-99-v1"
}
```

### 前置校验

- 当前用户是 Session owner；
- 用户拥有 project write 权限；
- Run.status == waiting_approval；
- 当前 pending Approval.action_code == save_generated_case_candidates；
- Approval.artifact_id == artifact_id；
- Artifact 属于同一 Session/Run；
- Artifact.type == test_case_set；
- Artifact.status 为 draft/reviewing/approved 中允许状态；
- candidate_ids 非空、唯一、全部存在；
- 不信任前端 candidate payload；
- 从 Artifact.payload_json 重新读取候选；
- 选中候选重新执行必要 Schema/业务校验；
- 当前来源重新计算 source_hash，必须等于 Artifact.source_hash；
- T06 已存在 source_changed warning 时也必须重新检查，不能只看 warning。

来源变化返回 409，禁止保存，Approval 保持 pending 或按明确策略处理。

### 保存实现

优先复用：

- save_generated_function_cases
- save_generated_api_cases

要求：

- project_id 以后端 RequirementDoc/ApiDocument 为准；
- module_id 策略与 V1 保持并在 API 文档说明；
- 只保存选中 candidate_ids；
- 单事务保证业务用例、Artifact、Approval、Run/Event 一致；
- 如 V1 save Service 内部自行 commit，必须评估原子性；必要时提出最小事务适配，但不得复制整套保存逻辑后产生两份规则；
- 如果无法在不修改 V1 Service 的前提下保证原子性，触发停止条件并报告，不得假装原子；
- APICase/FunctionCase 暂无 agent_run_id，Artifact 记录 saved_case_ids 和 target_type；
- 现有业务 source 字段如只能为 llm，保留当前值并登记限制，不擅自修改表结构。

### 保存幂等

当前模型没有单独 save idempotency 字段时，优先利用已存在的：

- Approval 只能从 pending 解决一次；
- Artifact.status/saved_case_ids；
- Run 终态；
- 请求 idempotency_key 与现有持久化字段的可用性。

必须给出可持久化、进程重启后仍有效的策略。不能用内存 set/cache。

若现有字段无法保存 save idempotency_key，允许采用“同一 save Approval 只能成功一次，重复请求读取 Artifact 中 saved_case_ids 并返回同一结果”的方案；冲突 candidate_ids 返回 409。

### 成功结果

```text
写入选中业务用例
→ Artifact payload 增加 saved_case_ids/selected_candidate_ids
→ Artifact.status=saved
→ Approval.status=approved + resolution_json
→ Run.status=succeeded
→ 写 cases_saved Event
```

## 十七、V1 Save Service 事务风险

当前 V1 保存 Service 可能自行 commit。

编码前必须明确选择以下之一：

1. 最小重构 V1 保存 Service，允许传入 `commit=False`，默认仍为 True，保持 V1 调用兼容；Agent Save 在外层统一 commit。
2. 新增共享的纯构建/flush 函数，由 V1 和 Agent 共用，旧接口行为不变。
3. 如果本任务内无法安全完成，停止并报告，不得用多次 commit 声称原子保存。

任何 V1 Service 修改必须：

- 签名默认行为兼容；
- T01 Baseline 继续通过；
- 增加 rollback 测试；
- 不修改 Router 调用；
- 在开发记录中精确说明。

## 十八、HTTP 错误合同

遵循项目现有 FastAPI 风格，至少区分：

- 400：业务输入不合法；
- 401：未登录；
- 403：无权限；
- 404：资源不存在；
- 409：状态冲突、重复不同请求、来源变化；
- 422：Pydantic 请求校验失败；
- 500：未处理内部错误，不返回 Secret。

Runtime 的 error_code 可以包含在安全响应中，但不能直接把内部 traceback 返回前端。
