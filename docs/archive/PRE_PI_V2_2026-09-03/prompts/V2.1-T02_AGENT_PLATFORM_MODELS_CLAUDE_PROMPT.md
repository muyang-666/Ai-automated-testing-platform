## 三、任务目标

为 TestMind 对话式测试 Agent 建立最小、可扩展、可审计的数据基础：

- AgentSession：一次持续对话工作空间
- AgentMessage：用户、Agent、系统和工具消息
- AgentEvent：可观察的运行与 GATE 事件
- AgentRun：Session 中一次具体 Skill 任务
- AgentStep：Run 的 LLM/Tool/Validation/Approval 步骤
- AgentArtifact：覆盖矩阵、用例集等结构化业务产物
- AgentApproval：保存、造数、重跑等人工审批

同时引入 Alembic，为后续 Agent 表和字段变更提供可回滚 migration。

SkillDefinition 和 ToolDefinition 首期保存在代码目录和注册表中，本任务不要创建 skill/tool 数据库表。

## 五、重要迁移现实

当前仓库没有 V1 的 Alembic 历史，因此不能假装一条新 migration 就能从空数据库完整创建全部 V1 + V2 表。

修改前必须提出并解释安全的“增量接管”方案，例如：

```text
0001_v1_schema_baseline
  - no-op baseline，代表当前已有 V1 schema

0002_agent_platform_tables
  - 只创建本任务 Agent 平台表

现有数据库：
  alembic stamp 0001_v1_schema_baseline
  alembic upgrade head

当前新环境：
  暂时仍由 create_all 创建 V1 schema
  然后按明确流程 stamp/upgrade
```

也可以提出更安全方案，但必须说明：

- 现有数据库如何接入；
- 新数据库如何初始化；
- upgrade/downgrade 的边界；
- create_all 在过渡期是否保留；
- 何时才能完全由 Alembic 管理全部 schema。

禁止：

- 对真实 MySQL 执行 migration；
- 自动生成一个试图重建全部现有 V1 表的未审查 migration；
- 删除或重建现有业务表；
- 声称“空数据库可完全 upgrade”但没有 V1 schema migration 证据。

如果主计划/验收清单与真实迁移条件冲突，先指出冲突并提出文档修订，等待用户确认。

## 八、建模规则

1. 一张表对应一个模型文件，遵循当前项目命名方式。
2. 使用 String status，不使用 MySQL ENUM，保持 SQLite 测试兼容。
3. JSON 大字段使用 SQLAlchemy JSON/Text 时说明选择理由。
4. 外键指向现有 users/projects 时，明确 ondelete 行为。
5. 不新增 ORM relationship，除非当前项目已有一致模式且确有消费者。
6. 所有 sequence_no 设计唯一约束，避免事件或步骤乱序。
7. idempotency_key 需要可执行的唯一性策略，不能只增加普通字段。
8. 不在 AgentStep/Event 中持久化 Secret、完整 API Key 或隐藏思维链。
9. status 的允许值需要在 Schema 或常量中集中定义，不能散落 magic string。
10. 不为 V2.2/V2.3 提前增加没有消费者的字段。
